Enrich the project's README with incremental NEW content. Do NOT replace or rewrite existing content — only add to it.

## Steps

1. **Read the current README** — Read the existing README.md (or README) file in the repo root. Understand what's already covered so you don't duplicate it.

2. **Explore the codebase** — Scan the project structure, key source files, configs, and tests to understand what was built and how it works. Look for architectural patterns, algorithms, design decisions, and anything notable.

3. **Identify gaps** — Compare what the README already covers against what could be documented. Consider these categories:
   - **Why it's useful** — motivation, problem it solves, who benefits
   - **How it works** — architecture overview, data flow, key abstractions
   - **Algorithms & design principles** — core algorithms, design patterns, trade-offs made
   - **Technical details** — performance characteristics, scaling considerations, limitations
   - **Project structure** — directory layout, key files, module responsibilities
   - **Configuration & customization** — available options, extension points
   - **Examples & usage** — additional usage scenarios, advanced examples
   - **Contributing & development** — how to set up locally, run tests, project conventions

4. **Draft new sections** — Write new markdown sections for the gaps you identified. Each section should be substantive (not just a sentence) and add real value. Use diagrams (mermaid), tables, or code blocks where they help.

5. **Append to the README** — Insert the new sections at appropriate locations in the existing README. Respect the existing structure and flow. Place new content where it logically fits — don't just dump everything at the bottom.

## Rules

- **Incremental only** — Never delete, rewrite, or restructure existing content. Only add.
- **Be substantive** — Each new section should teach the reader something meaningful about the project.
- **Match the tone** — Follow the writing style and formatting conventions already used in the README.
- **No fluff** — Skip generic filler like "this project is great". Focus on specific, useful information derived from the actual codebase.
